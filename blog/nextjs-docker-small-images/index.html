Shipping a Next.js App in a Tiny Docker Image

How multi-stage builds and Next.js standalone output took my image from over a gigabyte to something I'm not embarrassed to push.

Radharaman SethiAug 12, 20268 min read
🐳

The first time I put a Next.js app into a Docker image, I copied a Dockerfile from somewhere, ran docker build, and got an image well over a gigabyte. It worked — but pushing it took forever and every deploy felt sluggish.

Here's how I got it down to something sensible, and what I learned about Docker along the way.

Why the naive image is huge

The typical first attempt looks like this:

Dockerfile
FROM node:20
WORKDIR /app
COPY . .
RUN npm install
RUN npm run build
CMD ["npm", "start"]

Three problems hide in those six lines:

  • The full node base image ships compilers and tools you don't need at runtime.
  • All of node_modules — including dev dependencies like TypeScript and ESLint — ends up in the final image.
  • COPY . . before npm install means any source change invalidates the dependency layer, so every build reinstalls everything.

Step 1: Turn on standalone output

Next.js can trace exactly which files your server needs and copy them into a self-contained folder. Enable it in your config:

next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  output: "standalone",
};

export default nextConfig;

After next build, you get .next/standalone containing a minimal server.js and only the dependencies it actually uses. That alone is the biggest win.

Step 2: Use a multi-stage build

A multi-stage Dockerfile uses separate stages for installing, building and running. Only the last stage becomes your image — everything else is thrown away.

Dockerfile
# ---- 1. dependencies ----
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

# ---- 2. build ----
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NEXT_TELEMETRY_DISABLED=1
RUN npm run build

# ---- 3. runtime ----
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production NEXT_TELEMETRY_DISABLED=1

RUN addgroup -S nodejs && adduser -S nextjs -G nodejs

COPY --from=builder /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

USER nextjs
EXPOSE 3000
ENV PORT=3000 HOSTNAME=0.0.0.0
CMD ["node", "server.js"]
📌

The standalone folder does not include public/ or .next/static — you have to copy those yourself, as above. Forgetting this is the classic "my CSS and images are 404ing" bug.

Step 3: Respect the layer cache

Docker caches each instruction. Because the deps stage copies only package.json and the lockfile before running npm ci, that layer is reused until your dependencies actually change. Editing a component no longer triggers a full reinstall — rebuilds go from minutes to seconds.

Step 4: Add a .dockerignore

Without one, COPY . . sends your local node_modules, .next and .git into the build context:

.dockerignore
node_modules
.next
.git
Dockerfile
docker-compose.yaml
*.md
.env*

Excluding .env* also keeps local secrets from being baked into an image by accident.

The result

With standalone output, an Alpine base, a multi-stage build and a proper .dockerignore, the final image typically lands in the low hundreds of megabytes instead of over a gigabyte — and it runs as a non-root user, which is a nice security bonus. Check yours with:

bash
docker build -t my-next-app .
docker images my-next-app

Takeaways

  • Ship only what runs: output: "standalone" does the heavy lifting.
  • Build in one stage, run in another.
  • Order your COPY instructions from least- to most-frequently changed.
  • Always add a .dockerignore.

Small images aren't just about disk space — they mean faster deploys, faster scaling and a smaller attack surface. Worth the extra fifteen lines. 🐳
