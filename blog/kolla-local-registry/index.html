Running a Local Container Registry for Kolla-Ansible

Faster deploys, pinned images and air-gap readiness — how to mirror Kolla images into your own registry and point your cloud at it.

Radharaman SethiSep 28, 20267 min read
📦

Every Kolla-Ansible deployment is, at heart, a lot of container images. By default each host pulls them from a public registry. That's fine for a lab, but in a real cloud you quickly want three things the public registry can't give you: speed, consistency and control.

A local registry gives you all three. Here's how I set one up and wire Kolla-Ansible to it.

Why bother?

  • Speed. A dozen hosts each pulling a hundred images over the internet is slow. Pulling over your management network is fast.
  • Consistency. Every host gets exactly the same image digest, even if upstream publishes a new build halfway through your deploy.
  • Control. You decide when images change. Upgrades become a deliberate step, not a side effect of a restart.
  • Air-gap readiness. Once images are mirrored, your controllers and computes don't need internet access at all.
  • Custom images. If you build your own images with kolla-build, they need somewhere to live.

1. Run the registry

The simplest option is the standard registry:2 image on your deploy host. Kolla's own docs use port 4000, because 5000 is Keystone's port and the clash is a classic source of confusion:

bash
docker run -d --name registry --restart=always \
  -p 4000:5000 \
  -v registry:/var/lib/registry \
  -e REGISTRY_STORAGE_DELETE_ENABLED=true \
  registry:2

Put it on the management network, not on anything tenant-facing. For anything beyond a lab, give it TLS (a certificate from your internal CA) and authentication. Harbor is a good next step if you want a UI, RBAC and vulnerability scanning.

2. Mirror the images

Pull the images for your release, retag them for your registry and push. The exact tag format depends on the release and base distro, so check what upstream publishes for yours before scripting it:

bash
#!/usr/bin/env bash
# mirror-kolla.sh — copy Kolla images into a local registry
set -euo pipefail

SRC="quay.io/openstack.kolla"
DST="10.10.10.5:4000/openstack.kolla"
TAG="<release>-<distro>"   # e.g. what openstack_tag resolves to

for img in $(cat images.txt); do
  docker pull "$SRC/$img:$TAG"
  docker tag  "$SRC/$img:$TAG" "$DST/$img:$TAG"
  docker push "$DST/$img:$TAG"
done

Keep images.txt limited to the services you actually enable. There's no point mirroring hundreds of images you'll never run.

💡

Tools like skopeo copy can copy images registry-to-registry without storing them in the local Docker cache first, which saves a lot of disk on the deploy host.

3. Point Kolla-Ansible at it

A few lines in globals.yml do the rest:

yaml
# /etc/kolla/globals.yml (excerpt)
docker_registry: "10.10.10.5:4000"
docker_namespace: "openstack.kolla"
# only for a plain-HTTP lab registry; prefer TLS in production
docker_registry_insecure: yes
# if the registry needs auth:
# docker_registry_username: "kolla"
# docker_registry_password lives in passwords.yml

Then pre-pull to every host before you deploy. That way a slow or failed pull shows up on its own, instead of in the middle of a deploy:

bash
kolla-ansible pull -i multinode
kolla-ansible deploy -i multinode

4. Pin what you run

The registry only gives you control if you also pin tags. Mirror a new set of images under a new tag, test them in staging, and only then change the tag your production inventory uses. A rollback is just pointing back at the previous tag, because the old images are still in your registry.

5. Build your own images when you need to

Sometimes you need a patch or an extra package in an image. kolla-build can push straight to your registry:

bash
kolla-build --base ubuntu --registry 10.10.10.5:4000 --push nova

Use a distinct tag or namespace for custom builds so it's always obvious which hosts run modified images.

6. Housekeeping

Registries grow. With deletes enabled (as in step 1), delete old tags through the registry API, then run garbage collection to free the space:

bash
docker exec registry bin/registry garbage-collect /etc/docker/registry/config.yml

Run it in a quiet window, and keep at least the previous release's images around so you always have a known-good rollback.

Checklist

  • Registry on the management network, on a port that doesn't clash with Keystone
  • TLS and authentication for anything beyond a lab
  • Only the images you actually deploy are mirrored
  • docker_registry and docker_namespace set in globals.yml
  • kolla-ansible pull before every deploy or upgrade
  • Tags pinned, with the previous release kept for rollback

It's a small piece of infrastructure, but it turns deploys from "hope the internet behaves" into something boring and repeatable, which is exactly what you want. 📦
