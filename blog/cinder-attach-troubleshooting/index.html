Cinder Volume Won't Attach? Troubleshooting iSCSI and Ceph RBD

Volumes stuck in “attaching”, boot-from-volume failures and os-brick errors — where to look for LVM/iSCSI and Ceph-backed storage.

Radharaman SethiJul 30, 20268 min read
💾

Few things are as frustrating as a volume that won't attach. The API accepted the request, the volume sits in attaching or reserved, and the instance never sees a disk. Or a boot-from-volume instance fails with a vague block device mapping error.

Attachment touches Nova, Cinder, os-brick, the hypervisor and your storage backend all at once, so the trick is finding which layer actually failed. Here's how I approach it for the two backends I see most: LVM over iSCSI and Ceph RBD.

1. Read the state from both sides

Start with what Cinder and Nova each believe:

bash
openstack volume show <volume-id> -c status -c attachments
openstack server event list <server-id>
openstack server event show <server-id> <request-id>

Then grab the request ID and follow it through the logs. On Kolla, the useful ones are:

  • /var/log/kolla/cinder/cinder-volume.log on the storage or controller node: did Cinder export the volume?
  • /var/log/kolla/nova/nova-compute.log on the compute node: did os-brick connect to it? This is where most attach errors actually show up.
💡

A useful rule of thumb: if cinder-volume logged a successful initialize_connection but nova-compute shows an os-brick error, the problem is the path between the compute and the storage, not Cinder itself.

2. LVM / iSCSI: can the compute reach the target?

With the LVM driver, Cinder exports each volume as an iSCSI target and the compute node logs into it. Check from the compute:

bash
# can we discover targets on the address Cinder advertises?
iscsiadm -m discovery -t sendtargets -p <target-ip>:3260

# which sessions are currently logged in?
iscsiadm -m session

The usual culprits:

  • Wrong or unreachable target IP. The address Cinder advertises for the target (target_ip_address in the backend config) must be reachable from every compute, ideally over the storage network.
  • Two iscsid daemons. Kolla runs iscsid in a container on computes. If the host's own iscsid service is also running, they fight over sessions. Stop and disable the host service.
  • Firewalls blocking TCP 3260 between compute and storage nodes.
  • Duplicate initiator names in /etc/iscsi/initiatorname.iscsi, common when computes were cloned from the same image.
  • Stale sessions left over from earlier failed attempts. Log them out carefully once you're sure nothing is using them.

3. Ceph RBD: does the compute have the right keys?

With Ceph, there's no iSCSI. libvirt talks to Ceph directly, so attach problems are almost always about configuration and authentication:

bash
# does libvirt know the secret Nova expects?
docker exec nova_libvirt virsh secret-list

# does the Ceph user have the right capabilities?
ceph auth get client.cinder
  • Secret UUID mismatch. rbd_secret_uuid in Nova and Cinder must match a secret defined in libvirt on every compute, holding the right key.
  • Missing or wrong capabilities. The Cinder client user needs access to the volumes pool, and usually read access to the images pool for clones.
  • Missing config or keyring on a newly added compute. Kolla copies these from /etc/kolla/config/, so check the files are there for every service that needs them.
  • Network. Computes must reach the Ceph monitors and OSDs on the Ceph public network, and jumbo-frame mismatches there cause stalls that look like hangs.

4. Boot-from-volume specifics

When an instance boots from a volume, Nova creates the volume (often from an image) and then attaches it. Two extra failure points appear:

  • Image-to-volume conversion can be slow or fail on large images. Look for timeouts in cinder-volume.log. With Ceph, using RAW images lets Cinder clone instead of copying, which is dramatically faster.
  • Nova giving up while waiting for the volume to become available. Nova's block device allocation retry settings control how long it waits.

5. Cleaning up stuck volumes, carefully

Once you've fixed the cause, you may still have volumes stuck in attaching or detaching. Admins can reset them, but first confirm the volume really isn't attached: check the hypervisor (virsh domblklist) and the storage side. Resetting state on a volume that is actually in use is how data gets corrupted.

bash
# inspect attachments (newer Cinder API microversions)
cinder --os-volume-api-version 3.27 attachment-list --volume-id <volume-id>

# only after verifying nothing is using it
openstack volume set --state available --detached <volume-id>

My checklist

  1. Volume status and attachments, plus the server event list
  2. Follow the request ID: cinder-volume.log, then nova-compute.log
  3. iSCSI: target reachable, single iscsid, unique initiator names, no stale sessions
  4. Ceph: secret UUID, capabilities, config and keyring present, network and MTU
  5. Clean up stuck state only after verifying on the hypervisor

Attach failures feel random until you split them into layers. After that, they're usually one missing key, one unreachable IP, or one daemon too many. 💾
