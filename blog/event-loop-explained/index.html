The JavaScript Event Loop, Explained Like You're Waiting for Chai

Call stack, task queue, microtasks — why setTimeout(fn, 0) isn't really zero, and why your Promise logs first.

Radharaman SethiSep 28, 20267 min read
☕

Quick quiz. What does this print?

JavaScript
console.log("1: chai is ordered");

setTimeout(() => console.log("2: timeout"), 0);

Promise.resolve().then(() => console.log("3: promise"));

console.log("4: chai is served");

If you said 1, 4, 3, 2 — nice. If you're not sure why, grab a cup of chai. Let's walk through it.

JavaScript has one kitchen

JavaScript runs your code on a single thread. Picture a tiny chai stall with one person making drinks. They can only make one cup at a time. That one person is the call stack: whatever function is on top is what's being worked on right now.

So how does a single-threaded language handle timers, network requests and clicks without freezing? It delegates.

The helpers: Web APIs

When you call setTimeout or fetch, JavaScript hands the waiting part to the environment (the browser or Node.js). It's like the chai-wallah telling a helper, "Ping me in five minutes." The stall keeps serving other customers in the meantime.

When the helper is done, they don't barge in. They put a note in a queue.

Two queues, not one

This is the bit that trips everyone up. There are (at least) two queues:

  • The task queue (sometimes called the macrotask queue): callbacks from setTimeout, setInterval, I/O and UI events.
  • The microtask queue: Promise callbacks (.then, .catch, .finally, the code after await) and queueMicrotask.
☕

Think of microtasks as regulars at the counter — they get served the moment the current cup is done. Tasks are the queue outside, served one at a time, and only once the counter is clear.

The loop itself

The event loop is surprisingly simple. Roughly, it does this forever:

  1. Run whatever is on the call stack until it's empty.
  2. Run all microtasks — including any new ones added while running them.
  3. (In browsers) render if needed.
  4. Take one task from the task queue and go back to step 1.

Back to the quiz

Let's trace it:

  1. "1: chai is ordered" logs immediately — it's synchronous.
  2. setTimeout(..., 0) hands a timer to the environment. Its callback will go into the task queue.
  3. Promise.resolve().then(...) schedules its callback in the microtask queue.
  4. "4: chai is served" logs — still synchronous.
  5. The stack is empty, so the loop drains microtasks: "3: promise".
  6. Only now does it pick up the next task: "2: timeout".
setTimeout(fn, 0) doesn't mean "run now". It means "run after everything currently happening, and after every microtask."

Why this matters in real code

Long synchronous work blocks everything

If you run a heavy loop on the main thread, nothing else — not clicks, not timers, not rendering — gets a turn. The page freezes. Break the work into chunks, or move it to a Web Worker.

Microtasks can starve the page too

Because the loop drains all microtasks before moving on, a microtask that keeps scheduling another microtask will block rendering just as badly as a while (true):

JavaScript
// Don't do this — the page will never repaint
function forever() {
  Promise.resolve().then(forever);
}
forever();

async/await is just Promises

Everything after an await runs as a microtask. That's why code following an await always runs after the current synchronous code finishes — even if the awaited value is already available.

JavaScript
async function brew() {
  console.log("A");
  await null;
  console.log("C");
}

brew();
console.log("B");
// A, B, C

The one-sentence version

Run the stack to empty, drain every microtask, maybe paint, take one task, repeat. Once that sentence clicks, a whole category of "why is this running in the wrong order?" bugs simply disappears.

Now go finish that chai before it goes cold. ☕
