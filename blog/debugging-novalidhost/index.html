Debugging NoValidHost: A Field Guide

“No valid host was found” is Nova's least helpful error. Here's the order I check things in, from the fault message down to Placement inventory.

Radharaman SethiAug 20, 20267 min read
🔍

If you've run OpenStack for more than a week, you've seen it:

text
No valid host was found. There are not enough hosts available.

It's Nova's least helpful error. It tells you the scheduler gave up, but not why. Over time I've settled on a fixed order for chasing it down, starting with the cheapest checks and moving towards the deep ones. Here it is.

1. Read the fault, then the scheduler log

Start with what Nova recorded on the instance itself:

bash
openstack server show <server-id> -c fault -f yaml

The fault message is usually the generic sentence above, but it gives you a timestamp and request ID. Take that request ID to the scheduler log. On a Kolla-Ansible deployment, logs live under /var/log/kolla/ on the controllers:

bash
grep <request-id> /var/log/kolla/nova/nova-scheduler.log

Look for lines saying a filter returned 0 hosts. That one line usually turns "something is wrong" into "the AggregateInstanceExtraSpecsFilter rejected everything", which is a much better problem to have.

💡

If the scheduler log shows Placement returned no allocation candidates, the filters never ran. Skip straight to step 4: it's a capacity or inventory problem, not a filtering one.

2. Are the compute services actually up?

A surprising number of NoValidHost errors come down to compute nodes that Nova doesn't consider usable:

bash
openstack compute service list --service nova-compute
openstack hypervisor list

Check for three things:

  • State down: nova-compute isn't reporting in. Check its container and log on that host, and look at RabbitMQ connectivity.
  • Status disabled: someone (or something) disabled it, often during maintenance. Re-enable it with openstack compute service set --enable <host> nova-compute.
  • Missing hypervisor: a new compute node that never got mapped to a cell. Run nova-manage cell_v2 discover_hosts --verbose from a Nova container that has nova-manage.

3. Check what the request is actually asking for

Before blaming capacity, look at the flavor and the image. Both can carry constraints that quietly shrink the set of eligible hosts:

bash
openstack flavor show <flavor> -c vcpus -c ram -c disk -c properties
openstack image show <image> -c properties
  • Flavor extra specs that point at a host aggregate no compute node belongs to.
  • Image properties (hw_*, architecture, hypervisor type) that no host can satisfy.
  • Availability zone requests that point at a zone with no healthy hosts.
  • Server groups with an anti-affinity policy and more members than you have hosts.

4. Ask Placement directly

Placement tracks every compute node as a resource provider with an inventory (VCPU, MEMORY_MB, DISK_GB) and usage. With the osc-placement plugin installed, you can ask the same question the scheduler asks:

bash
# can ANY provider satisfy this request?
openstack allocation candidate list \
  --resource VCPU=4 --resource MEMORY_MB=8192 --resource DISK_GB=40

# inspect one provider's inventory and usage
openstack resource provider list
openstack resource provider inventory list <rp-uuid>
openstack resource provider usage show <rp-uuid>

If the candidate list is empty, compare usage with total × allocation_ratio − reserved for each resource. The usual culprits are:

  • Allocation ratios set lower than you think. In Kolla-Ansible these are set through a nova.conf override, so check what's actually deployed rather than what you remember setting.
  • Disk: DISK_GB depends on your storage backend. With local ephemeral disks it's per host. With RBD-backed ephemeral disks, every compute node reports the same shared Ceph pool, so one nearly full pool can make every host look full at once. Boot-from-volume flavors with a 0 GB root disk don't request DISK_GB at all.
  • Leaked allocations from deleted or failed instances that still hold resources. Placement's heal_allocations and audit tooling in nova-manage placement can help, but read what they'll change before you run them.

5. Think about the real capacity

Sometimes the answer is honest: you're out of room. Fragmentation is the sneaky version, where the cluster has 64 free vCPUs in total but no single host has 8. Cluster-wide totals hide this, while per-provider usage shows it immediately.

NoValidHost is rarely one big failure. It's usually one small constraint you forgot was there.

My checklist

  1. Fault and request ID → scheduler log → which filter returned 0 hosts?
  2. Compute services up, enabled and mapped to a cell?
  3. Flavor extra specs, image properties, AZ and server groups?
  4. Placement allocation candidates, inventory, usage and allocation ratios?
  5. Real capacity and per-host fragmentation?

Working through it in this order has turned most of my NoValidHost tickets from hour-long hunts into ten-minute fixes. 🔍
