Planning the Network for a Kolla-Ansible OpenStack Cloud

Bonds, VLANs, jumbo frames and VIPs — a practical way to lay out the networks before you run your first kolla-ansible deploy.

Radharaman SethiSep 15, 20268 min read
🧭

Most painful OpenStack problems I've seen trace back to decisions made before the first kolla-ansible deploy: which traffic shares a wire, where the MTU changes, and which interface Neutron is allowed to own. Networks are much harder to change after day one than services are.

This is the general approach I use when planning one. The addresses below are documentation ranges, not any real environment, so swap in your own.

Separate traffic by trust and by volume

A typical multi-node cloud has at least these kinds of traffic. Each one deserves its own VLAN, and usually its own subnet:

NetworkCarriesMTU
Management / internal APISSH, Ansible, internal endpoints, DB, RabbitMQ1500
TunnelVXLAN tenant overlay between computes and network nodes9000
Storage publicCeph clients: RBD for Nova, Cinder and Glance9000
Storage clusterCeph OSD replication only9000
Public APIExternal VIP for Horizon and public endpoints1500
External / providerRouter gateways and floating IPs1500

The point isn't the exact list. It's that a noisy Ceph rebalance should never be able to starve your API traffic, and tenant traffic should never share a broadcast domain with your database.

Two bonds, two jobs

A pattern that has served me well on controllers and computes:

  • bond0 carries host VLANs as sub-interfaces (bond0.10, bond0.20 …). These have IP addresses.
  • bond1 is handed entirely to Open vSwitch as a provider trunk (br-ex). It has no host IP. Neutron owns it.

In Kolla-Ansible terms, that maps neatly onto network_interface (management), tunnel_interface, api_interface, and neutron_external_interface:

yaml
# /etc/kolla/globals.yml (excerpt)
network_interface: "bond0.10"
api_interface: "bond0.10"
kolla_external_vip_interface: "bond0.50"
tunnel_interface: "bond0.20"
neutron_external_interface: "bond1"
kolla_internal_vip_address: "10.10.10.10"
kolla_external_vip_address: "203.0.113.10"
⚠️

Never give neutron_external_interface an IP address or use it for anything else. Once OVS takes it over, anything the host was doing on it stops working, and that's a very confusing way to lose SSH.

Jumbo frames, end to end or not at all

Running tunnel and storage traffic at MTU 9000 is worth it, but only if every hop agrees. That includes host interfaces, bonds, VLAN sub-interfaces and every switch port in between, which usually need 9216 to allow for headers.

Test it before you deploy anything:

bash
# 8972 = 9000 minus 28 bytes of IP + ICMP headers; -M do forbids fragmentation
ping -M do -s 8972 <peer-on-tunnel-vlan>

Also remember VXLAN's overhead. If the underlay is 9000, tenant networks need to be around 8950. Get this wrong and you'll see the classic symptom: SSH connects, then hangs the moment you run anything that prints more than a screen.

Give every host exactly one default route

Multi-homed hosts with several gateways cause asymmetric routing that looks like random packet loss. Pick one default route per host role. For example, controllers route out through the public API network and everything else through management. Use specific routes for anything else.

VIPs, HAProxy and TLS

Kolla-Ansible puts HAProxy and keepalived in front of the APIs with two virtual IPs: an internal one on the management network and an external one on the public network. Plan DNS names for both early, because your TLS certificates need them. Retrofitting TLS onto a running cloud is a lot more work than starting with it.

Plan for the things you'll add later

  • Octavia needs a management network that controllers can reach and amphora VMs can attach to, so it often has to be present on both bonds.
  • Physical devices (lab hardware, appliances) are easiest to bring in as extra provider VLANs on the same bond1 trunk.
  • Out-of-band management (BMC / IPMI) belongs on its own network, completely outside the cloud.

A pre-deploy checklist

  1. Every traffic type mapped to a VLAN, subnet and MTU.
  2. Switch ports configured as LACP trunks with the right VLANs and MTU 9216.
  3. Jumbo-frame ping succeeds between every pair of hosts on 9000-MTU networks.
  4. The external interface has no IP and nothing else depends on it.
  5. One default route per host, and DNS names and certificates ready for both VIPs.

None of this is glamorous. But every hour spent here saves a day of chasing "intermittent" problems later. 🧭
