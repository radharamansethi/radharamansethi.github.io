When the Control Plane Wobbles: RabbitMQ and MariaDB Galera

API calls hang, instances sit in BUILD and logs fill with MessagingTimeout. A calm, ordered way to check HAProxy, RabbitMQ and Galera.

Radharaman SethiSep 2, 20268 min read
🐇

Some OpenStack failures are loud. Control-plane problems are usually quiet: API calls that take thirty seconds, instances stuck in BUILD, volumes that never leave creating, and logs full of MessagingTimeout. Nothing is obviously down, yet nothing works.

Most of the time the cause is one of three shared services that every OpenStack project depends on: HAProxy, RabbitMQ and MariaDB Galera. Here's the order I check them in on a Kolla-Ansible deployment.

ℹ️

Commands use docker. If your deployment uses Podman, swap in podman. Logs live under /var/log/kolla/ on each host.

1. Where is the VIP, and is HAProxy happy?

Every service reaches the database and APIs through the internal VIP, which keepalived floats between controllers. First confirm exactly one controller holds it:

bash
# run on each controller
ip -brief address | grep <internal-vip>

Zero holders means nothing can reach the APIs. Two holders (split brain) causes very strange, intermittent failures. Check the keepalived container logs in both cases.

Then look at HAProxy's view of the backends. Kolla exposes a stats page (port 1984 by default) that shows which backends are up, down or flapping. A single API container marked down on one controller is a very different problem from all of Galera being marked down.

2. RabbitMQ: is the cluster whole?

OpenStack services talk to each other over RabbitMQ. If messages can't flow, API calls succeed but the actual work never happens.

bash
docker exec rabbitmq rabbitmqctl cluster_status
docker exec rabbitmq rabbitmqctl list_queues name messages consumers \
  | awk '$2 > 0' | sort -k2 -n | tail

What I look for:

  • Running nodes should list every controller. A missing node, or a reported network partition, is your problem.
  • Queues with messages but zero consumers: the service that should consume them is down or has lost its connection.
  • Steadily growing queues: consumers are alive but too slow, or stuck.
  • Memory or disk alarms in the RabbitMQ logs. When an alarm triggers, RabbitMQ blocks publishers, which looks exactly like a hang.

Restart RabbitMQ containers one at a time, checking cluster_status before moving to the next node. Restarting all of them at once risks the cluster failing to re-form.

💡

If you're still on classic mirrored queues, plan a move to quorum queues. Recent Kolla-Ansible releases support them and they handle node failures far more predictably.

3. MariaDB Galera: is the cluster primary and synced?

Galera is a synchronous multi-master cluster. It only accepts writes while it has quorum. Check every node:

bash
docker exec mariadb mysql -u root -p -e \
  "SHOW STATUS WHERE Variable_name IN \
   ('wsrep_cluster_size','wsrep_cluster_status', \
    'wsrep_local_state_comment','wsrep_ready');"
VariableHealthy valueIf not…
wsrep_cluster_sizeNumber of controllersA node has dropped out. Check its logs and network
wsrep_cluster_statusPrimaryThe node lost quorum and refuses writes
wsrep_local_state_commentSyncedDonor or Joining means the node is still catching up, so wait
wsrep_readyONThe node won't serve queries

The root password is in /etc/kolla/passwords.yml as database_password.

If the whole cluster went down, for example after a power loss, Galera won't restart by itself, because it doesn't know which node has the latest data. Kolla-Ansible has a dedicated command for exactly this:

bash
kolla-ansible mariadb_recovery -i multinode

It finds the most advanced node and bootstraps the cluster from it. Don't try to bootstrap by hand unless you know which node has the newest state. Picking the wrong one throws away transactions.

4. Then restart the consumers

Here's the step people forget. After RabbitMQ or Galera recovers, some services keep holding broken connections and stay stuck. Check their logs for repeated reconnect errors, and restart them in a sensible order:

bash
# controllers
docker restart nova_conductor nova_scheduler neutron_server cinder_scheduler
# computes (one at a time is fine)
docker restart nova_compute neutron_openvswitch_agent

5. Prevent the next one

  • Monitor the basics: Galera cluster size and status, RabbitMQ partitions, queue depth and alarms, and VIP location.
  • Watch disk on controllers. A full disk is a classic trigger for RabbitMQ alarms and a stalled Galera.
  • Keep clocks in sync. Clock drift causes confusing token and message problems.
  • Write the recovery runbook before you need it, and practise it on a staging cloud.
The control plane rarely fails all at once. It degrades, and the faster you can tell which of the three shared services is unhappy, the shorter the outage.

Run in this order (VIP and HAProxy, then RabbitMQ, then Galera, then consumers), these checks turn a scary "everything is broken" into a short, specific list. 🐇
