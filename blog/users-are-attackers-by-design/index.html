When Your Users Are Attackers by Design

Isolation lessons from 2026's OpenStack and KVM disclosures — hypervisor, image pipeline, tenant network and browser console.

Radharaman SethiOct 5, 20269 min read
🔐

In most clouds, a tenant who attacks the platform is an incident. On a cyber range, it is the curriculum. Participants get root on their machines, attack tooling, and an explicit mandate to probe, pivot and escalate. That makes a range the most adversarial tenant population an OpenStack cloud can host.

2026 has been a busy year for OpenStack and KVM security disclosures. Four of them map neatly onto the four isolation layers any OpenStack cloud with untrusted tenants depends on: the hypervisor, the image pipeline, the tenant network, and the browser console. Cyber ranges are the extreme case, so I'll use them as the lens. The same reasoning applies to any public or shared OpenStack cloud.

Layer 1: The hypervisor boundary (CVE-2026-53359, "Januscape")

On July 4, 2026, NVD published CVE-2026-53359, a use-after-free in the Linux kernel's KVM x86 shadow MMU, disclosed publicly as Januscape. It is not an OpenStack bug, but every KVM-based OpenStack compute node inherits it. According to the public disclosure, a guest can trigger it on Intel and AMD hosts when nested virtualization is exposed. A denial-of-service proof of concept is public, and the researcher reports a working guest-to-host escape in a controlled environment.

The highest-risk profile reads like a description of a cyber range: x86 KVM hosts, untrusted multi-tenant guests, root inside the guest, and nested virtualization available. Ranges are tempted to enable nested virtualization because some exercises need it, such as running a hypervisor-based malware lab or a virtual appliance that is itself a VM host.

What this means for a range: nested virtualization should be a deliberate, scoped capability, never a fleet-wide default. It can be exposed at several layers, so a review has to check all of them:

  • Host KVM module settings for nested support
  • libvirt CPU mode, especially host-passthrough and host-model
  • Flavor extra specs, image properties and host aggregates that expose CPU features
  • Whether running guests can actually see the vmx (Intel) or svm (AMD) flag

Where an exercise genuinely needs nested virtualization, it belongs on a dedicated host aggregate, so a breakout cannot reach other tenants' workloads. When patching, check your distribution's backported fixes rather than trusting uname -r alone, because enterprise kernels often keep older version strings.

Layer 2: The image pipeline (CVE-2026-24708)

In February 2026, OSSA-2026-002 disclosed that Nova invoked qemu-img without format restrictions during resize. A crafted disk image could abuse this to overwrite arbitrary files on the compute host. Fixed releases are Nova 30.2.2, 31.2.1 and 32.1.1, and downstream vendors shipped patches.

Cyber ranges consume more third-party images than almost any other cloud. A single scenario can combine vendor firewalls, routers, VPN gateways, IDS/IPS sensors, WAFs, SD-WAN appliances and deliberately vulnerable targets, often sourced from many different places. Each one is a disk image the hypervisor host will parse.

What this means for a range: treat image intake as a supply chain, not a file upload.

  • Restrict who can upload images to Glance, and keep participants out of that path entirely
  • Inspect and normalize images offline before they reach production, using tools such as qemu-img info and virt-inspector
  • Set explicit image properties (disk format, machine type, NIC and video models) rather than relying on auto-detection
  • Keep Nova patched. Format-handling bugs recur, and this fix only closed one code path

Layer 3: Tenant network isolation (Neutron ownership bugs)

Neutron had a run of authorization flaws this summer that share one root cause: an API checked permission on one object, then acted on another without confirming they belonged together.

CVE-2026-55707 (OSSA-2026-032)Aug 2026Onboard another project's shared-network subnets into their own subnet pool, altering the victim's L3 routing and address scopeNeutron 28.0.2

CVE-2026-49299Jun 2026As a project manager, create a port on another project's shared network with a network: device owner such as network:dhcpNeutron 28.0.1

None of these is a dramatic remote exploit. But on a range, participants are actively encouraged to enumerate and abuse the platform's APIs, and an unpatched cross-project bug turns a training exercise into a real tenant-to-tenant breach.

What this means for a range: avoid giving participants OpenStack API credentials wherever possible, and minimize shared networks between tenants.

  • Participants interact with their lab through the range's own portal, not Horizon or the OpenStack CLI
  • Each team or exercise gets its own project and networks. Reserve shared networks for platform services
  • Security groups follow an allow-only model: remove the default egress-allow rule and add only what the scenario needs
  • Clean up stale ports, networks and security groups routinely, because orphaned resources are attack surface nobody is watching

Layer 4: The browser console (OSSN-0101)

In July 2026, OSSN-0101 described a flaw in Nova's console WebSocket proxy, the component behind the browser VNC console. On every request, the proxy appended the client-supplied Host header to a shared, process-wide allowed-origins list, and those entries stayed there until the process restarted. An unauthenticated attacker could add arbitrary hostnames to the list, defeating the Origin check for every later request, and slowly exhaust memory along the way.

For most clouds, the console is an occasional admin convenience. For a cyber range, it is the front door: participants spend hours in browser consoles, and the console proxy is directly reachable from the networks they work from.

What this means for a range: put the console behind your own access layer instead of exposing the stock proxy directly.

  • Front the console with a reverse proxy that enforces authentication, TLS and a strict Host and Origin policy before traffic reaches Nova
  • Issue console sessions through the range portal, tied to the participant's role and current exercise
  • Treat the noVNC client as a maintained dependency, kept current like any other frontend library
  • Watch console proxy memory and restart behavior. Slow memory growth was this bug's only visible symptom

Design principles, layer by layer

The common thread is one working assumption: every participant VM is hostile, and every layer must hold even if the one above it fails.

Layer2026 disclosurePrinciple
HypervisorCVE-2026-53359 (Januscape)Nested virtualization only where a scenario requires it, never as a default CPU feature
Image pipelineCVE-2026-24708Curated images, inspected and tested before they enter Glance. No participant uploads
Tenant networkCVE-2026-55707, OSSN-0102, CVE-2026-49299No participant API credentials, per-exercise projects and networks, and allow-only security groups
Console accessOSSN-0101Consoles brokered through a portal and hardened reverse proxy, never the raw Nova proxy

Two habits carry a lot of the weight in practice. First, automated hygiene: scheduled cleanup of orphaned resources, with dry-run defaults, backups before deletion and age guards so live exercises are never touched. Second, appliance compatibility testing: validate every virtual firewall, router, IDS and WAF image before it appears in a scenario.

A checklist for cyber range operators

  • Confirm whether any guest can see vmx or svm, and whether it should
  • Verify compute host kernels against your distribution's Januscape advisory
  • Upgrade Nova and Neutron past the fixed releases listed above
  • Remove participant access to OpenStack APIs, Horizon and image upload
  • Audit shared networks and cross-project RBAC policies
  • Put a hardened reverse proxy in front of the console proxy
  • Schedule cleanup of orphaned network resources
  • Subscribe to OpenStack Security Advisories and Security Notes

Closing thoughts

None of this year's disclosures was unique to cyber ranges. But a range is where they matter most, because the people most likely to find and use them are already logged in and being rewarded for it. Isolation on a range cannot rest on any single layer. The hypervisor, the image pipeline, the network and the console each need their own controls, so that one advisory never becomes one breach.

If you run a range, a training lab or any OpenStack cloud with untrusted tenants, I'd be glad to compare notes.
